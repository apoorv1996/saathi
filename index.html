Saathi — a voice assistant for auto drivers to understand their earnings

Drivers can ask questions like “kal kitna kamaya?” or “paise kyun kate?” in Hindi or Hinglish. Saathi checks the driver's own trip data and replies by voice in Hindi.

Try the live app Read the PRD
Built by Apoorv Singhal · October 2026

Why I built this

While working at Uber on the Auto category, I worked with a lot of drivers, both cab drivers and auto drivers. Many of them were unable to interact with the application through its interface. Their earnings, incentives and fines were all in the app, but they could not easily understand them. That is where the motivation for this project came from.

I have recently started learning how LLMs work and how AI products are built. I built this prototype for two reasons:

  1. To understand how these applications are actually built.
  2. To build something useful that I can relate to my past experience.

How I built it

I built this app using AI, and I don't want to hide that. The coding was done by AI. I reviewed the code, identified what purpose it needs to solve, and took the trade-offs and decisions that came up while building. Then I tested it to confirm that it solves my use case.

My idea was to learn how the entire application is built, so I built it step by step, one version at a time.

Started with a PRD

I started with a product requirements document (PRD). I structured the PRD myself: the opportunity, the users and their problems, the sections, the requirements, and which parts should be done by AI and which by code. I filled it in and then refined it using AI. I also used AI to identify how the document could be improved and whether I was missing any edge cases. For example, “kal” can mean both yesterday and tomorrow, and what the app should do when the AI's answer cannot be trusted.

Version by version

  • v1
    Basic chatbot. Answered based on keywords with fixed Hindi replies, no AI. This helped me understand how the speech and voice APIs work. Problem: almost every question got the same earnings answer.
  • v2
    AI understands the question. An LLM identifies what the driver is asking and for which dates. While reviewing, I found that the dates were often wrong, it reported the wrong fine, and it skipped days where data was missing without telling the driver.
  • v3
    Code does all the calculations. The AI only identifies the question. Code calculates the dates and every number. Safety words like “accident” go directly to a human agent. If data is missing, the app says so. I also added a set of test questions.
  • v4
    Follow-up questions. While testing, the app told me about a ₹50 fine. When I asked “why was it deducted?”, it said there was no deduction, because it did not remember the previous answer. I added follow-up questions, a login with two demo drivers, a check that refuses questions about other drivers, and a phone-style interface.
  • v5
    Explains the “why”. Testing showed that it repeated the same answer and could not explain how fees or incentives work. I added a knowledge base of policies, let the AI write the reply while code checks every number in it, and made it offer a human agent instead of repeating an answer. Switching to Sarvam's real-time model reduced the reply time from 20–40 seconds to 4–6 seconds.

Decisions I took

  • Follow-up questions should work. A driver will ask “kyun?” after an answer, so the app needs to remember the conversation.
  • A driver can see only their own data. The driver is identified from the login, not from what they say. Questions about other drivers are refused.
  • Never give the same answer twice. If the driver asks again, the first answer did not help. So the app offers to transfer the call to customer service, even though this means more calls to support.
  • “Why” questions need policy, not just numbers. A knowledge base lets the app explain how the incentive or fee was calculated, using the driver's own trips.
  • Show the data behind the answers. The demo shows each driver's full data and the policies below the app, so anyone can verify the answers.

How it works

Flow of one question

AI is used only to understand the question and write the reply. Everything that needs to be exactly right is done by code.

Sarvam speech APISarvam LLMPlain code
  1. Driver speaks or typesLogged in, so the app already knows the driver ID.
  2. Clean the audioCodeffmpeg converts it to 16 kHz mono, 0.5 to 30 seconds.
  3. Speech to text · Saaras v3Sarvam APICodemix mode keeps Hinglish exactly as spoken.
  4. Safety keyword checkCodeWords like accident, police, block, fraud (in English and Hindi script) go to a human agent.
  5. Other-driver checkCodeAnother driver's name or ID gets a polite refusal.
  6. Understand the question · LLM call 1Sarvam LLMsarvam-105b-conversations returns the topic, “how much” or “why”, and the time period.
  7. Dates and calculationsCode“kal” becomes 20 Oct; code adds up trips, fee, incentive and fines from the driver's data.
  8. Repeat checkCodeThe same question again gets an offer to transfer to customer service.
  9. Write the reply · LLM call 2Sarvam LLMA short Hindi reply from the facts sheet and the knowledge base.
  10. Number checkCodeIf the reply has any number not in the data or rules, a fixed template reply is used.
  11. Text to speech · Bulbul v3Sarvam APIHindi voice reply, played in the app.

What is used

  • Sarvam APIs: Saaras v3 (speech to text, codemix mode), sarvam-105b-conversations (LLM, reasoning off, temperature 0), Bulbul v3 (Hindi voice, speaker “Shubh”).
  • Data: dummy driver data (two drivers, 1–21 Oct 2026) and a knowledge base of policies (platform fee, incentive slabs, fines, payouts).
  • App: Python with Gradio, a phone-style web interface, hosted on Hugging Face Spaces.
  • There is no separate translation step. Saaras writes down the Hinglish as spoken, the LLM reads it directly and writes the reply in Hindi, and Bulbul speaks it.

Rules the app always follows

  • AI never does calculations. Code calculates every number.
  • Every number the driver hears is checked against their data and the policy.
  • A driver can never see another driver's data.
  • Safety words skip the AI, so they work even if the AI is down.
  • If data is missing, the app says so instead of guessing.
  • The same answer is never given twice.

How I tested it

An AI app can sound right and still be wrong, so I test it in layers. So far I have run the first two. Each one checks a different part of the flow above.

1. Code tests

50 small checks on the parts done by plain code: every day's numbers add up, safety words go to a human, questions about other drivers are refused, follow-ups use the right dates, and the login works. These don't call the AI, so they run in a second and are free.

2. Does the AI understand the question?

A fixed list of 45 driver questions in Hindi, Hinglish and English, each with the right answer written down: what the driver is asking about and for which dates. The test sends each question to the AI and compares.

50 / 50code tests passed
39 / 45questions fully correct (86%)
43 / 45dates correct

Dates were the main problem in v2. Now every question with a time in it was correct: kal, parson, pichhle hafte, “12 se 15 tarikh”, and follow-ups like “aur parson?”.

What I learned: the AI is now reliable on the core job (earnings, dates, follow-ups). It is weak on questions outside that job. The next version will fix these, and I will re-run the same 45 questions to compare.

Still to test

  • The spoken reply: is every number right, does it answer what was asked, is it short and simple Hindi.
  • Real voices: recordings from drivers, with traffic noise.
  • Full conversations: follow-ups, repeats and safety words in the middle of a chat.
  • Speed: time taken for each step.
